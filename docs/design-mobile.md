# 移动端（Android）设计方案

> 状态：**设计稿**，尚未开工。本文的用途是——当新会话开始做 Android 端时，照着它就能落地，不必再从桌面端代码里重新考古。
> 结论先行：移动端**不复用** Spring Boot 后端与 Tauri 壳，但必须**严格复用两份契约**——`.tiku` 内容包格式与广场 API。

## 1. 目标与不做什么

**目标**：手机上完成"看题、做题、错题复习、导入导出、逛广场、发布作品"这一整条主线，交互按手机的用法重做，而不是把桌面界面缩小。

**做什么**
- 离线优先：无网也能做题、复习、看错题；数据存本机。
- 手机擅长的：碎片时间刷题、拍照/选图导入、复习提醒推送、随时看统计。
- 与桌面同账号、同广场、同文件格式：桌面导出的 `.tiku` 手机能导入，反之亦然。

**不做什么**
- 不做 Spring Boot / JVM：Android 上跑完整 Spring Boot + H2 不现实（体积、启动、电量、进程模型都不合适）。
- 不做桌面 UI 的平移（侧栏 + 多栏 + 表格在手机上不可用）。
- 不做实时云同步（本轮）：跨设备靠广场与 `.tiku` 文件。
- 不做"打印试卷"（手机无打印场景）→ 改为**导出 PDF / 分享**（Android 的 `PrintManager` 或分享 Intent）。

## 2. 技术选型

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 语言/UI | Kotlin + Jetpack Compose (Material 3) | 唯一主流原生方案；声明式 UI 与桌面端 Vue 的思路一致，迁移心智成本低 |
| 架构 | MVVM + 单向数据流（ViewModel + StateFlow + Repository），多模块按功能切分 | 与现有"service 承载业务规则"的习惯对应，便于逐条搬运规则 |
| 本地库 | Room（SQLite）+ 手写迁移 | 表结构与桌面端 H2（`MODE=MySQL`）基本可一一对应；Room 的迁移可与 Flyway 版本号对齐 |
| 网络 | Retrofit + OkHttp + kotlinx.serialization | 广场 API 是 HTTP/JSON，契约见 `docs/api.md` |
| 图片 | Coil | 题目内嵌图、广场封面 |
| 后台任务 | WorkManager | AI 导入是长任务，需要断点续传/失败重试；复习提醒用 `WorkManager` 定期任务 |
| 偏好存储 | DataStore(Proto/Preferences) | 对应桌面端的 `ai-config.json` / `export-prefs.json` / `center-auth.json` |
| 公式渲染 | 由简到繁：先 KaTeX or MathJax 放进一个最小 WebView 只渲染公式片段；后续再评估原生渲染 | 桌面端用 KaTeX，公式语法（LaTeX）必须保持一致，否则同一道题两端显示不同 |
| 富文本 | Compose `AnnotatedString` + 自定义 parser，把 `[图片:xxx]` 标记与公式片段切成分段渲染；复杂表格段落用 WebView 兜底 | 与桌面端同一套标记语法 |

**为什么不选其他路**
- Flutter：能复用 UI 代码，但等于第三套渲染与生态，且要重建所有原生能力（文件、分享、后台任务）——本项目不需要"一套 UI 三端跑"。
- 移动网页版 / PWA：AI 导入需要大量本地文件处理与后台长任务，浏览器里体验与稳定性都差；而且官网本身不开源，把它变成 App 会牵动整个后端形态。
- 直接把桌面 jar 塞进 Android（Termux 类）：不可行，不作为产品方案。

## 3. 必须守住的契约（不可协商）

1. **`.tiku` / 内容包 JSON 格式**：字段、命名规则、校验规则以 `docs/package-format.md` 为准。移动端解析器必须与桌面端通过同一批样例文件（`sample-content-package.json` + 至少 3 个真实导出包）验证一致。
2. **广场 API**：端点、鉴权、错误码以 `docs/api.md` 为准；桌面端目前经本地后端代理，移动端可直连，但**认证方式必须兼容**（cookie 会话不适合 App，建议复用 Bearer + 一次性 ticket 的桌面流程，或新增 App 专用 OAuth deep link）。
3. **业务规则**（照搬，不重新发明）：
   - 错题口径：最近一次作答为错才算错；主观题自评 `PARTIAL`/`WRONG` 算错；未自评不算错。
   - 复习算法：答对 `level+1`（封顶 5）、间隔 `min(2^level,30)` 天；答错 `level=0`、立即到期。
   - 主观题判分：满分 / 半分 / 0（`CORRECT`/`PARTIAL`/`WRONG`）。
   - 会话模式：`ALL`/`SEQUENCE`/`TOPIC`/`REVIEW`/`WRONG`/`FAVORITE`；材料题按材料分成"单元"连续出现。
   - 版本号自增规则与文件名规则（`{题库名或packageKey}-{版本}.tiku`）。
4. **i18n**：手机端同样要中英双语；文案可与桌面端共用一份 key 表（把桌面端组件字典抽成 JSON 资源，是顺手可做的收益）。

| 主观题自评 | 写答案（含手写？v1 先用文本）→ 展示参考答案 → 三档按钮自评 | M1 |
| 错题本 / 复习队列 | 独立 Tab，支持"今日待复习 N 题"一键开始 | M1 |
| 学习统计 | 首页卡片 + 统计页（热力图、正确率、题库维度），点击数字直达对应动作 | M1 |
| 统计里的会话历史 | 列表 + 详情（可续做） | M2 |
| 录题/编辑 | 简化为"新建题目"表单（选项增删、图片从相册/相机插入） | M2 |

| 导出 `.tiku`/JSON | 走系统分享面板 / SAF 选择目录 | M2 |
| 广场（浏览/搜索/收藏/评论/关注/下载导入） | 原生列表 + 详情页；下载后一键导入 | M2 |
| 发布作品 | 简化为"选择本地题库 → 填版本说明 → 上传"（不做目录导出那一步，本机即源） | M2 |
| 账号（注册/登录/邮箱验证/找回/GitHub） | 原生表单 + 系统浏览器 OAuth + deep link 回调 | M2 |
| AI 批量导入 | 拍照/选图/选 PDF → 上传解析 → 预览校对（手机上以"逐题卡片 + 快速修正"为主，不做大表格） | M3 |
| AI 配置（BYOK） | 设置页选择供应商模板 + 填 Key + 测试连通（本地模型地址概念在手机上意义较小，可保留） | M3 |
| 复习提醒 | 本地通知（WorkManager 定时检查到期题数） | M3 |
| 打印试卷 | **不做**；改为导出 PDF / 系统打印 | — |
| 备份恢复（整目录替换+重启） | 改为"导出全量备份文件 / 从文件恢复"，不做自动重启 | M3 |
| 自动更新 | 应用商店 / 官方 APK 检查更新 | M3 |
| 双语文案 | 全量支持 | M1 |

## 5. 信息架构与导航

底部四个 Tab（Material 3 NavigationBar）：

1. **题库**：我的题库列表 → 题库详情（题目 / 错题 / 复习 / 统计 / 设置）
2. **刷题**：今日待复习 + 继续上次会话 + 快捷入口（错题重做、随机练习）
3. **发现**：广场（搜索、分类、榜单）→ 题库详情 → 下载导入
4. **我的**：账号、我的作品（发布/管理）、导入导出、AI 配置、外观与语言、关于

一级页面关系（文字版）：

```
题库 ─┬─ 题库详情 ─┬─ 题目列表 ─ 题目详情/编辑
      │            ├─ 错题本
      │            ├─ 复习队列
      │            └─ 统计（该库）
      └─ 新建/导入
刷题 ─┬─ 复习会话
      ├─ 错题会话
      └─ 上次会话继续
发现 ─┬─ 广场列表 ─ 题库详情 ─ 下载导入
      ├─ 作者主页
      └─ 搜索
我的 ─┬─ 账号/登录
      ├─ 我的作品 ─ 发布/改版本/下架
      ├─ 导入导出（含 .tiku 分享接收）
      ├─ AI 配置
      └─ 设置（外观/语言/通知/关于）
```

## 6. 关键交互设计

**做题（核心体验）**
- 一屏一题：题干区可滚动（公式/图片正常显示），选项区固定在下方易于拇指点选。
- 材料题：题干上方横向可折叠的材料卡片，滑出即看，不离开当前题。
- 交卷/下一题：底部主按钮；已选但未提交时按钮高亮，防误触退出（返回键提示"已作答未提交"）。
- 答题卡：底部抽屉，网格显示已答/未答/标记；点击跳题。
- 选择题提交后：立即显示对错 + 解析（可在设置里改为"交卷后统一看"）。
- 主观题：文本输入（后续可加手写板）→ 三档自评；自评按钮要大、可单手触达。

**复习**
- "今日待复习 N 题"作为刷题 Tab 的主入口；复习会话结束给"明天还有 M 题"的正反馈。
- 单题可"暂停复习"（长按/更多菜单），与桌面一致。
- 可选每日固定时间本地通知（默认关闭，避免打扰）。

**导入**
- 注册 `Intent` 过滤器接收 `.tiku`/`.json`（从微信/QQ/浏览器"用拾题打开"直接进导入流程）——这是手机上最重要的导入路径，桌面端没有的入口。
- 预览页显示：题库名、版本、题目数、来源、是否有图；确认后写入 Room（事务）。

**发布**
- 从"我的题库"里选一个 → 自动算下一个版本号（同一套自增规则）→ 填更新说明 → 上传（进度条 + 可取消）。
- 大包上传要考虑断网重试：用 WorkManager 做可恢复上传（OkHttp 支持 `Content-Range` 或分片，视服务端能力而定；服务端是否支持分片上传需要先确认——见第 9 节）。

## 7. 数据模型映射

桌面端数据目录：`{TIKU_DATA_DIR:-~/.tiku}`，H2 文件库 `tiku.mv.db`（`MODE=MySQL`），图片在数据目录下按日期分目录（`/api/banks/{bankId}/images/{date}/{file}`）。

映射到移动端（Room）：

| 桌面（H2） | 移动端（Room） | 说明 |
| --- | --- | --- |
| `question_bank` | `QuestionBankEntity` | 字段一一对应；`review_enabled` 保留 |
| `question` | `QuestionEntity` | 选项/答案用 JSON 文本列（与桌面一致），不要拆表——这是格式契约的一部分 |
| `material` | `MaterialEntity` | 同上 |
| `study_record` | `StudyRecordEntity` | 记录只增不改；`is_correct` 可空语义必须保留（主观题） |
| `review_state` | `ReviewStateEntity` | 主键 = 题目 id |
| `practice_session` / `practice_session_question` | 同名两张表 | 会话恢复功能依赖它 |
| `review_*` / `stats` | **不落表**，按需聚合查询 | 桌面端统计也是现算 |
| `export_records` | 可省略（手机端无"导出目录"概念），但发布记录建议保留 | 用于"我的作品"状态 |
| 图片文件 | 应用私有目录 + 记录相对路径 | 不要存绝对路径；导入导出时按格式重映射（见内容包规范） |

**迁移/互通方式**：不做数据库级迁移（H2 文件 Android 读不了）。互通只走两条路——
1. `.tiku` / JSON 内容包（题目与材料，跨端换题库）；
2. 学习记录 JSON（`/api/study-records/export|import`，跨端换刷题进度）。

> 建议：把"学习记录 JSON"也纳入正式契约文档（当前在 `docs/api.md` 里有一节），并在两端加同一批样例的往返测试。

## 8. 与广场/服务端的配合

- 移动端**直连** `https://pickq.cn`（不像桌面端那样经本地后端代理），因此需要：
  - App 专用登录回调：`pickq://auth/callback`；服务端要把它加入 GitHub OAuth 回调白名单（当前白名单只允许 `http://127.0.0.1:{port}/api/center/auth/github/callback`，需要**新增移动端规则**）。
  - 若沿用"一次性 ticket 换 token"的桌面流程，服务端要确认 ticket 对 App 同样可用（当前实现是通用的一次性 ticket 表）。
- 需要新增/确认的服务端能力（开工前先与官网侧确认）：
  1. 移动端 OAuth 回调白名单与 deep link；
  2. 大文件上传是否支持分片/断点续传（当前是 multipart 直传，限制 210MB 请求体；手机上弱网大包风险高）；
  3. 客户端版本与最低支持版本握手（用于强制升级提示）；
  4. 可选的推送（当前无推送通道；提醒先用本地通知，不做服务端推送）。

## 9. 里程碑建议

**M1（可用的刷题器，能独立发布）**
Room 数据模型 + `.tiku`/JSON 导入导出 + 题库/题目/错题/复习/统计 + 做题会话（六种模式）+ 主观题自评 + 中英双语 + 深色模式。

**M2（账号与社区）**
账号体系（含 deep link OAuth）、广场浏览/搜索/下载导入、收藏/评论/关注、我的作品与发布、Intent 接收 `.tiku`。

**M3（AI 与打磨）**
AI 批量导入（拍照/PDF）、AI 配置、复习提醒、导出 PDF/分享、备份文件导出与恢复、性能优化（万题级列表与搜索）。

## 10. 风险与坑（提前知道能省很多时间）

1. **公式与富文本**：两端渲染差异会立刻被用户发现。建议先做"标记解析 + 公式渲染"的共用测试样例集（含表格、下标、根号、图片混排）。
2. **大题库性能**：桌面端靠分页 + 后端查询；手机端要在 Room 里建好索引（`bank_id`、`question_key`、`package_key`），列表用 Paging 3。
3. **图片路径**：桌面端图片是"数据目录 + 相对路径"，Android 上应用私有目录在升级/清理时行为不同——务必只存相对路径，导出时重新打包进 `.tiku`。
4. **主观题判分不能"自动判"**：不要为了体验自作主张给主观题打分，会破坏错题与统计口径。
5. **错题口径**：实现时直接照抄第 3 节的规则并写单测；这是最容易被"顺手优化"写错的地方。
6. **AI 导入的长任务**：手机上不能像桌面那样常驻后台，必须用 WorkManager + 任务表（对应桌面端的 `ai_import_job`），任务可恢复。
7. **不要改动服务端未确认的接口**：广场 API 是线上合约，`web/` 不可随意改（不开源，且线上有真实用户）。

- `docs/architecture.md` —— 整体架构、启动链路、Android 复用/不复用清单
- `docs/features.md` —— 功能与业务规则（错题口径、复习算法、判分规则）
- `docs/code-map.md` —— 功能 → 代码位置对照，移植时按表逐块对照
- `docs/conventions.md` —— 编码与契约约定（移动端沿用同一套命名与错误语义）
- `sample-content-package.json` —— 最小示例包
- `docs/import-issues.md` —— 解析层的已知坑（移动端做导入会对上同类问题）

**样例数据（需要从桌面端导出，建议放入 `docs/samples/`，不入 git 或按需脱敏）**
- 3-5 个真实 `.tiku`：单选择题库、含材料大题、含图片与公式的理科卷、主观题为主、超大题库（>1000 题，用于性能测试）
- 1 份导出的学习记录 JSON（用于验证跨端进度互换）
- 1 份广场下载的包（验证服务端产出的包能被解析）

**服务端侧需要确认的问题（给官网维护者的清单）**
1. 移动端 OAuth 回调白名单如何加（deep link scheme）；
2. 大包上传是否需要分片接口；
3. 是否允许 App 直连现有 `/api/**`（限流与人机验证策略是否要区分客户端）；
4. 最低支持版本握手接口是否需要新增。

**建议的技术验证（半天内可完成的 spike）**
1. 用 Kotlin 解析 `sample-content-package.json` 与一个真实 `.tiku`，与桌面端解析结果逐字段比对；
2. 在 Compose 里渲染一段含图片标记与 LaTeX 的题干，确认观感可接受；
3. 直连广场 API 拉一次题库列表 + 下载一个包（验证鉴权与 TLS）。
